# 部门层级与数据范围权限 — 深度分析

> 日期：2026-06-01
> 背景：在现有设计文档 `组织架构与数据范围方案分析.md` 基础上，针对五个核心架构问题进行深入分析。

---

## 问题一：部门管理员只能查看、创建和编辑本部门及子部门的用户

### 分析

现有设计中，部门信息通过 `OrganizationClaimsTransformer` 注入 Claims，`DataScopeService` 将其翻译为 `VisibleUserIds` 集合。部门管理员角色绑定 `DataScope = CurrentAndChildren`。

### 实现方案

**查询（列表/搜索/详情）：**

Identity 模块的用户查询 Handler 注入 `IDataScopeService`，叠加可见用户过滤：

```csharp
// GetUsersQueryHandler — 改造后
public async ValueTask<PaginatedResult<UserDto>> Handle(
    GetUsersQuery query, CancellationToken ct)
{
    var filter = await _scopeService.GetFilterAsync(ct);

    var queryable = _dbContext.Users.AsNoTracking();

    if (!filter.IsAllDepartments)
    {
        // 部门管理员只能看到本部门及子部门的用户
        queryable = queryable
            .Where(u => _dbContext.UserDepartments
                .Where(ud => filter.VisibleDepartmentIds.Contains(ud.DepartmentId))
                .Select(ud => ud.UserId)
                .Contains(u.Id));
    }

    return await queryable
        .OrderBy(u => u.LastName)
        .PaginateAsync(query.Page, query.PageSize, ct);
}
```

**创建用户：**

部门管理员创建用户时，新用户自动分配到管理员的主部门：

```csharp
// RegisterUserCommandHandler — 创建用户后
var primaryDeptId = _scopeService.GetPrimaryDepartmentId();
if (primaryDeptId is not null)
{
    var assignment = UserDepartmentAssignment.Create(
        user.Id, primaryDeptId.Value, isPrimary: true);
    _dbContext.UserDepartmentAssignments.Add(assignment);
}
```

**编辑用户：**

编辑前校验目标用户是否在可见范围内：

```csharp
// UpdateUserCommandHandler
var targetDeptIds = await _dbContext.UserDepartmentAssignments
    .Where(ud => ud.UserId == command.UserId)
    .Select(ud => ud.DepartmentId)
    .ToListAsync(ct);

var filter = await _scopeService.GetFilterAsync(ct);
if (!filter.IsAllDepartments
    && !targetDeptIds.Any(d => filter.VisibleDepartmentIds.Contains(d)))
{
    throw new ForbiddenException("无法编辑不在管辖范围内的用户");
}
```

**关键点：** 部门管理员的权限来自"角色权限（能做什么）+ 数据范围（能看到什么数据）"两个维度的叠加。权限决定能否调用接口，数据范围决定接口返回哪些数据。

## 问题二：创建者部门异动导致数据归属错乱

### 问题描述

现有设计通过 `CreatedBy`（创建者 UserId）+ 运行时查询创建者当前部门来确定数据归属。当创建者从部门A调往部门B后：

- 他之前创建的数据 `CreatedBy` 仍然指向他
- 但数据范围查询时，查到他的当前部门是B
- 结果：**历史数据"跟随"创建者漂移到了新部门，但业务上这些数据应留在原部门**

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A: 存储 OwnerDepartmentId（推荐）** | 实体创建时记录创建者当时的主部门ID，后续数据范围直接以此字段过滤 | 数据归属明确、查询高效（单列索引）、创建者异动不影响 | 每个业务实体需加一个字段 |
| B: 创建者异动时重新分配数据 | 用户调岗时，批量更新其创建数据的部门归属 | 数据归属始终正确 | 复杂、高风险、大量写操作、不适合大数据量 |
| C: 存储创建快照表 | 单独建表记录"UserId→DepartmentId"的历史映射，查询时 JOIN | 不改业务实体 | 查询复杂、JOIN 性能差、快照表需维护 |

### 推荐方案：方案 A — `IHasDepartment` 接口

在 `BuildingBlocks/Core/Domain/` 中新增一个轻量接口（仅此一处对 Building Blocks 的修改）：

```csharp
// BuildingBlocks/Core/Domain/IHasDepartment.cs
namespace FSH.BuildingBlocks.Core.Domain;

/// <summary>
/// 标记实体需要进行部门数据范围隔离。
/// 实体创建时由拦截器自动填充 OwnerDepartmentId。
/// </summary>
public interface IHasDepartment
{
    /// <summary>数据所属部门的 Id。null 表示未分配部门（跨部门可见）。</summary>
    string? OwnerDepartmentId { get; set; }
}
```

**自动填充机制：**

在 `AuditableEntitySaveChangesInterceptor` 中增加对 `IHasDepartment` 的处理：

```csharp
// 在 SavingChangesAsync 中，创建新实体时自动填充
foreach (var entry in entries.Where(e => e.State == EntityState.Added))
{
    if (entry.Entity is IHasDepartment deptEntity
        && deptEntity.OwnerDepartmentId is null)
    {
        deptEntity.OwnerDepartmentId = _currentUser.GetPrimaryDepartmentId();
    }
}
```

**查询过滤变为：**

```csharp
// 改造后 — 直接用 OwnerDepartmentId 过滤，无需 JOIN 用户表
if (!filter.IsAllDepartments)
{
    queryable = queryable
        .Where(e => filter.VisibleDepartmentIds.Contains(e.OwnerDepartmentId!));
}
```

**为什么这解决了异动问题：**

- 数据创建时 `OwnerDepartmentId` 被"冻结"为创建者的当时部门
- 创建者后续调往任何部门，`OwnerDepartmentId` 不变
- 数据始终归属于创建时的部门，符合业务直觉
- 如果业务需要"数据随人走"，由管理员手动批量重新分配

### 与现有 `IAuditableEntity.CreatedBy` 的关系

两者共存，职责不同：

| 字段 | 用途 | 随创建者异动？ |
|------|------|--------------|
| `CreatedBy` (已有) | 审计追溯——谁创建的 | 不适用（审计快照） |
| `OwnerDepartmentId` (新增) | 数据范围过滤——属于哪个部门 | 不随创建者异动 |

## 问题三：部门管理和数据范围权限管理是否需要分开两个独立模块？

### 分析

| 维度 | 部门管理 | 数据范围权限 |
|------|---------|-------------|
| 核心实体 | Department, Position, UserDepartmentAssignment | RoleDataScope, DataScope 枚举 |
| 消费者 | Admin UI（组织架构页面） | 所有业务模块的 Handler |
| 变更频率 | 低（组织架构相对稳定） | 低（角色-范围映射相对固定） |
| 对外接口 | Department CRUD, Position CRUD | IDataScopeService |
| 内部实现 | 部门树维护、缓存 | Claims 转换、过滤条件生成 |

### 结论：**不需要拆分为两个模块，放在一个 `Organization` 模块中即可**

理由：

1. **强内聚** — 数据范围权限的数据源就是部门结构本身。`DataScopeService` 的 `VisibleDepartmentIds` 依赖 `DepartmentTreeService` 来递归解析。分开意味着要么循环依赖，要么引入不必要的中间层。

2. **Contracts 已提供足够隔离** — `Organization.Contracts` 暴露 `IDataScopeService`、`DataScope` 枚举、DTOs，消费者只依赖接口，不感知内部实现。部门管理（Department CRUD）和数据范围（DataScopeService）在运行时项目中是两个独立的 Feature 文件夹即可：
   - `Features/v1/Departments/` — 部门 CRUD
   - `Features/v1/Positions/` — 职位 CRUD
   - `Features/v1/RoleDataScopes/` — 角色数据范围配置
   - `Services/DataScopeService.cs` — 数据范围过滤引擎
   - `Services/DepartmentTreeService.cs` — 部门树查询

3. **参考 Identity 模块的先例** — Identity 模块同时管理用户、角色、权限、组、会话、模拟授权，没有拆成多个模块。Organization 的复杂度远低于 Identity。

4. **如果将来需要拆分也很容易** — 只要 Contracts 接口设计好，运行时实现迁移到新模块对外部消费者完全透明。

## 问题四：Group 和 Department 的关联关系

### 现有 Group 的定位

当前 Group 是一个**扁平**的用户集合，通过 `GroupRole` 绑定角色，实现"给一群用户批量授权"。但有一个关键缺陷：`UserPermissionService` 在解析用户权限时**没有调用 `GroupRoleService.GetUserGroupRolesAsync()`**，意味着 Group 分配的角色目前不生效。

### Group vs Department 的本质区别

| 维度 | Group | Department |
|------|-------|------------|
| 结构 | 扁平（无层级） | 树形（ParentId 递归） |
| 用途 | "你能做什么" — 权限打包 | "你能看到什么数据" — 数据范围 |
| 类比 | 项目组、兴趣小组、跨部门虚拟团队 | 行政组织架构（研发部→后端组→中间件团队） |
| 成员变更 | 随时加入/退出 | 正式调岗流程 |
| 生命周期 | 项目结束即解散 | 长期稳定存在 |

### 推荐方案：**独立共存，各司其职**

**Group 不改动** — 继续作为"权限打包"的工具。修复 `UserPermissionService` 使其包含 Group 派生的角色。

**Department 仅负责数据范围** — 不参与权限计算。用户的"能做什么"完全由角色（直接分配 + Group 派生）决定，用户的"能看到什么数据"由 Department + RoleDataScope 决定。

```
用户请求 → 认证(JWT) → 鉴权(角色+权限Claim)
                      → 数据范围(Department Claim → DataScopeService → VisibleDepartmentIds)
```

### 为什么不绑定 Group 和 Department？

1. **现实场景不需要** — 研发部的某员工可以同时属于"年终晚会筹备组"这个 Group（获得活动管理权限），Group 跨部门是常态。

2. **1:1 绑定过于死板** — 如果每个 Department 自动对应一个 Group，那么跨部门项目组（跨部门 Group）就无法建模。

3. **如果要限制 Group 成员来源** — 这是未来的可选项：给 Group 加一个可选的 `DepartmentId` 字段，表示"此 Group 的成员必须来自该部门"。这不是当前必须的功能，可以后续按需添加。

### 部门管理员权限的实现路径

部门管理员的"管理员"身份可以用两种方式获得：

- **方式 A（简单）**：直接给用户分配"部门管理员"角色（通过 `IdentityUserRole`）
- **方式 B（灵活）**：创建一个"部门管理员"Group，把用户加入该 Group，Group 绑定"部门管理员"角色（通过 `GroupRole`）

两种方式的效果相同——用户获得相同的一组权限 Claim。区别在于管理的便利性（批量 vs 逐个）。推荐同时支持两种方式。

## 问题五：是否需要抽象接口 + 模块数据范围分类

### 接口设计

**需要新增一个接口：`IHasDepartment`**（定义见问题二）。

原因：
1. 数据归属必须在创建时"冻结"，不能依赖运行时的创建者部门查询
2. 编译时约束——标记哪些实体参与部门数据范围隔离
3. 方便 `AuditableEntitySaveChangesInterceptor` 统一自动填充
4. 与现有的 `IHasTenant`（租户隔离）、`IGlobalEntity`（全局实体）形成一致的模式

**不需要**在 `BaseDbContext` 中增加全局查询过滤器（不像 `ISoftDeletable` 或租户过滤那样自动生效）。原因：

- 数据范围过滤不是"全局默认开启"的——不同模块、不同角色的过滤逻辑不同
- 有些接口需要跨部门查询（如租户管理员的"全部数据"视图）
- 过滤条件取决于 `DataScope`（全部门/本部门及子部门/仅本部门/自定义），不是简单的 `WHERE OwnerDepartmentId = currentUserDepartmentId`
- 因此过滤应该在 Handler 层由 `IDataScopeService` 显式调用，保留控制权

### 各模块数据范围分类

```
需要数据范围权限的模块
├── Catalog ★     品牌/分类/产品 —— 部门级业务数据，需实现 IHasDepartment
├── Tickets ★     工单 —— 部门级业务数据，需实现 IHasDepartment
├── Files ★       文件元数据 —— 部门级，已按 CreatedByUserId 过滤，改为 IHasDepartment
├── Identity ◆    用户管理 —— 部门管理员只能管理管辖范围内的用户（不修改 FshUser 本身）
└── Auditing ◆    审计日志查询 —— 部门管理员只能查看管辖范围内的操作记录

不需要数据范围权限的模块
├── Billing       租户级计费数据，无部门维度
├── Multitenancy  平台级租户管理，仅 Root 可见
├── Webhooks      系统级配置，仅 Admin 可见
├── Chat          已按频道成员隔离，无需部门维度
├── Notifications 已按 UserId 隔离，无需部门维度
└── Organization  部门管理本身由权限控制（Departments.Manage），不按部门过滤
```

**图例：** ★ = 实体需实现 `IHasDepartment`，◆ = Handler 注入 `IDataScopeService` 进行查询过滤

### Catalog 实体改造示例

```csharp
// 改造前
public sealed class Brand : AggregateRoot<Guid>, ISoftDeletable
{
    public string Name { get; private set; } = default!;
    public string? Description { get; private set; }
    // ...
}

// 改造后 — 仅加一个接口
public sealed class Brand : AggregateRoot<Guid>, ISoftDeletable, IHasDepartment
{
    public string Name { get; private set; } = default!;
    public string? Description { get; private set; }
    public string? OwnerDepartmentId { get; set; }  // ← IHasDepartment
    // ...
}
```

### Identity 模块的特殊处理

`FshUser` 本身**不需要**实现 `IHasDepartment`。用户不属于某个部门的数据实体——用户-部门的关联通过 `UserDepartmentAssignment` 表来表达。Identity 模块的改造仅限于：

1. 用户查询相关的 Handler 注入 `IDataScopeService`，基于 `UserDepartmentAssignment` 做 JOIN 过滤
2. 部门管理员只能操作管辖范围内的用户

### 为什么 Auditing 不需要 IHasDepartment

审计日志的 `CreatedBy` 是历史快照，不应随用户部门异动而改变归属。审计日志按 `CreatedBy → UserDepartmentAssignment → Department` 的路径实时查询即可——因为审计关注的是"谁在什么时候做了什么"，而"当时那人属于哪个部门"可以通过历史 UserDepartmentAssignment（配合软删除+Temporal Table）追溯。如果不需要那么精确的历史追溯，用 JOIN 查询当前部门即可。

## 总结：与现有设计文档的关键差异

| 决策点 | 现有设计文档 | 本文案建议 | 理由 |
|--------|------------|-----------|------|
| 数据归属字段 | 复用 `CreatedBy` + 运行时查部门 | 新增 `IHasDepartment.OwnerDepartmentId` | 避免创建者异动导致数据归属错乱（问题二） |
| 模块拆分 | 单一 Organization 模块 | 同意，单一模块即可 | 内聚性高（问题三） |
| Group 与 Department | 未涉及 | 独立共存，各司其职 | Group=权限打包，Department=数据范围（问题四） |
| 接口抽象 | 无 | 新增 `IHasDepartment` | 编译时约束 + 自动填充 + 模式一致（问题五） |
| 全局过滤 | 无（Handler 层过滤） | 同意，保持 Handler 层过滤 | 数据范围不是全局默认行为 |
| Building Blocks 变更 | 零侵入 | 仅新增 `IHasDepartment` 接口（~12行） | 最小化侵入，换取数据归属正确性 |
