# 组织架构（部门/职位）与数据范围控制方案分析

> 更新日期：2026-05-29
> 需求背景：在现有项目基础上扩充部门和职位，落地树形行政架构，各层级账户只能访问本级及子级数据。
> 设计约束：Organization 模块对 Building Blocks **零侵入**；每个角色绑定一种数据权限范围。

---

## 一、可行性结论

**完全可行。** 项目现有的审计体系已经为数据范围控制铺好了路：

- `IAuditableEntity` 自动记录 `CreatedBy`（创建者 UserId）—— 所有实现该接口的实体天然具备"谁创建的"追踪能力，数据范围过滤无需额外加字段。
- `ICurrentUser.GetUserClaims()` 已暴露所有 Claims —— Organization 模块无需修改 `ICurrentUser` 接口即可从中读取部门信息。
- 租户隔离已经由 Finbuckle 全自动处理 —— 部门范围是租户内的第二层过滤，互不干扰。
- `PermissionConstants.Register()` 动态注册 —— 新增权限零侵入。

**核心设计原则**：Organization 模块的一切能力通过其 `.Contracts` 项目对外暴露；Building Blocks 一行不改。

### 2.2 Organization 模块如何注入部门信息

部门信息通过 **标准 ASP.NET Core 的 `IClaimsTransformation`** 注入到当前请求的 `ClaimsPrincipal` 中，完全不需要修改 Identity 模块的 Token 颁发逻辑：

```
请求到达
  → CurrentUserMiddleware 设置 ICurrentUser（已有，不动）
  → Authentication 中间件解析 JWT，获得 TenantId + UserId + Roles
  → IClaimsTransformation 被调用
      → OrganizationClaimsTransformer 根据 UserId 查询部门分配
      → 添加 Claim("department_ids", "guid1,guid2,guid3")
      → 添加 Claim("primary_department_id", "guid1")
      → 添加 Claim("position_id", "guidX")
  → ICurrentUser.GetUserClaims() 即可读取到上述 Claim
```

**关键文件（全部在 Organization 模块内部）**：

```csharp
// Modules.Organization/Services/OrganizationClaimsTransformer.cs
internal sealed class OrganizationClaimsTransformer : IClaimsTransformation
{
    private readonly IUserDepartmentService _userDeptService;

    public async Task<ClaimsPrincipal> TransformAsync(ClaimsPrincipal principal)
    {
        if (principal.Identity is not { IsAuthenticated: true })
            return principal;

        var userId = principal.FindFirstValue(ClaimTypes.NameIdentifier);
        if (string.IsNullOrEmpty(userId))
            return principal;

        var assignments = await _userDeptService.GetAssignmentsAsync(userId);
        if (assignments is null or { Count: 0 })
            return principal;

        var identity = new ClaimsIdentity("Organization");
        identity.AddClaim(new Claim(OrgClaimTypes.DepartmentIds,
            string.Join(',', assignments.Select(a => a.DepartmentId))));
        identity.AddClaim(new Claim(OrgClaimTypes.PrimaryDepartmentId,
            assignments.FirstOrDefault(a => a.IsPrimary)?.DepartmentId.ToString() ?? string.Empty));
        identity.AddClaim(new Claim(OrgClaimTypes.PositionId,
            assignments.FirstOrDefault(a => a.IsPrimary)?.PositionId?.ToString() ?? string.Empty));

        principal.AddIdentity(identity);
        return principal;
    }
}
```

## 三、数据权限四级模型

### 3.1 DataScope 枚举

定义在 `Modules.Organization.Contracts` 中：

```csharp
namespace FSH.Modules.Organization.Contracts;

public enum DataScope
{
    /// <summary>全部门 — 租户内全部数据，无过滤</summary>
    AllDepartments = 1,

    /// <summary>本部门及子部门 — 当前部门 + 所有下级部门的数据</summary>
    CurrentAndChildren = 2,

    /// <summary>仅本部门 — 严格只看当前部门数据</summary>
    CurrentOnly = 3,

    /// <summary>自定义 — 管理员指定一个部门列表</summary>
    Custom = 4,
}
```

### 3.2 角色 → DataScope 映射

每个角色绑定一个固定的 DataScope，存储在 Organization 模块：

```
┌─────────────────────┬───────────────────────┬─────────────────────────────┐
│ 角色                 │ DataScope              │ 可见范围                      │
├─────────────────────┼───────────────────────┼─────────────────────────────┤
│ Root (平台超管)       │ AllDepartments         │ 全平台，跨租户（租户隔离已处理）  │
│ Admin (租户管理员)    │ AllDepartments         │ 本租户内全部部门数据             │
│ DeptManager (部门经理)│ CurrentAndChildren     │ 本部门 + 所有子孙部门            │
│ DeptMember (部门成员) │ CurrentOnly            │ 仅本部门                      │
│ Basic (基础用户)      │ CurrentOnly            │ 仅本部门（如无部门则仅本人）      │
│ CustomScope (自定义)  │ Custom                 │ 管理员指定的部门列表             │
└─────────────────────┴───────────────────────┴─────────────────────────────┘
```

映射配置实体：

```csharp
// Modules.Organization/Domain/RoleDataScope.cs
public sealed class RoleDataScope : BaseEntity<Guid>, IHasTenant
{
    public string RoleName { get; private set; } = default!;        // "DeptManager"
    public DataScope Scope { get; private set; } = DataScope.CurrentOnly;
    public List<Guid>? CustomDepartmentIds { get; private set; }    // 仅 Custom 时有效

    public static RoleDataScope Create(string roleName, DataScope scope,
        List<Guid>? customDeptIds = null)
        => new() { RoleName = roleName, Scope = scope, CustomDepartmentIds = customDeptIds };
}
```

初期使用硬编码默认值，后续可通过 Admin 管理界面动态调整。

### 3.3 DataScope → SQL 过滤的翻译

`IDataScopeService` 的核心职责：将当前用户的 `DataScope` 翻译为可用的过滤条件：

```csharp
// Modules.Organization.Contracts/Services/IDataScopeService.cs
public interface IDataScopeService
{
    /// 返回当前用户的数据范围过滤器。
    /// IsAllDepartments = true 意味着无需额外过滤（Admin/Root）。
    ValueTask<DataScopeFilter> GetFilterAsync(CancellationToken ct = default);
}

public sealed record DataScopeFilter
{
    public DataScope Scope { get; init; }
    public bool IsAllDepartments { get; init; }

    /// IsAllDepartments 为 true 时为 null，否则为可见用户 ID 的集合
    public IReadOnlySet<string>? VisibleUserIds { get; init; }

    public static DataScopeFilter AllDepartments
        => new() { Scope = DataScope.AllDepartments, IsAllDepartments = true };
}
```

`DataScopeService` 内部实现逻辑：

```
GetFilterAsync():
  1. 从 ICurrentUser.GetUserClaims() 读取 DepartmentIds
  2. 查询 RoleDataScope 表，获取当前角色对应的 DataScope
  3. 根据 Scope 翻译：
     AllDepartments    → IsAllDepartments = true
     CurrentAndChildren → 查询部门树，递归获取所有子孙部门 ID
                          → 查询这些部门中的用户 ID → VisibleUserIds
     CurrentOnly       → 查询本部门用户 ID → VisibleUserIds
     Custom            → 读取 CustomDepartmentIds，递归获取子部门
                          → 查询这些部门中的用户 ID → VisibleUserIds
  4. 返回 DataScopeFilter
```

## 四、其他模块引入数据权限的方式

### 4.1 整体模式

每个业务模块通过以下步骤接入数据权限：

```
1. 项目引用 Modules.Organization.Contracts（此前已有 Contracts 依赖习惯）
2. Handler 构造函数注入 IDataScopeService
3. Handle 方法开头调用 GetFilterAsync()
4. 用 VisibleUserIds 过滤查询
```

**不动 DbContext、不动实体、不动 Building Blocks。**

### 4.2 标准 Handler 改造（模板）

```csharp
// 改造前（Catalog/SearchBrandsQueryHandler.cs）
public sealed class SearchBrandsQueryHandler
    : IQueryHandler<SearchBrandsQuery, PaginatedResult<BrandDto>>
{
    private readonly CatalogDbContext _dbContext;

    public async ValueTask<PaginatedResult<BrandDto>> Handle(
        SearchBrandsQuery query, CancellationToken ct)
    {
        var brands = await _dbContext.Brands
            .AsNoTracking()
            .Where(b => b.Name.Contains(query.SearchKeyword))
            .OrderBy(b => b.Name)
            .PaginateAsync(query.Page, query.PageSize, ct);

        return brands.Adapt<PaginatedResult<BrandDto>>();
    }
}

// 改造后 — 仅加 3 行
public sealed class SearchBrandsQueryHandler
    : IQueryHandler<SearchBrandsQuery, PaginatedResult<BrandDto>>
{
    private readonly CatalogDbContext _dbContext;
    private readonly IDataScopeService _scopeService;               // ← 新增

    public SearchBrandsQueryHandler(
        CatalogDbContext dbContext,
        IDataScopeService scopeService)                              // ← 新增
        => (_dbContext, _scopeService) = (dbContext, scopeService);

    public async ValueTask<PaginatedResult<BrandDto>> Handle(
        SearchBrandsQuery query, CancellationToken ct)
    {
        var filter = await _scopeService.GetFilterAsync(ct);        // ← 新增

        var queryable = _dbContext.Brands.AsNoTracking()
            .Where(b => b.Name.Contains(query.SearchKeyword));

        if (!filter.IsAllDepartments)                                // ← 新增
            queryable = queryable
                .Where(b => filter.VisibleUserIds!.Contains(b.CreatedBy));

        var brands = await queryable
            .OrderBy(b => b.Name)
            .PaginateAsync(query.Page, query.PageSize, ct);

        return brands.Adapt<PaginatedResult<BrandDto>>();
    }
}
```

### 4.3 实体没有 CreatedBy 怎么办？

`IAuditableEntity` 提供了 `CreatedBy`（类型是 `string?`，存的是 `UserId.ToString()`）。
目前项目中 **所有通过 `BaseDbContext` 的业务实体** 均受 `AuditableEntitySaveChangesInterceptor` 覆盖，新增即自动填充。

如果某个实体确实没有 `CreatedBy`（比如 Billing 模块的实体，它继承的是普通 `DbContext`），有两种处理方式：

| 场景 | 处理方式 |
|------|---------|
| 实体已经实现 `IAuditableEntity` | 直接用 `.CreatedBy` 过滤（推荐） |
| 实体未实现，但需要部门隔离 | 手动加 `CreatedByUserId` 属性，建索引，创建时赋值 |
| 实体不需要部门隔离 | 不引入 `IDataScopeService`，保持原样 |

### 4.4 非列表接口（详情/更新/删除）的改造

查询单个实体时同样需要校验数据范围：

```csharp
// 详情接口示例
var entity = await _dbContext.Brands
    .AsNoTracking()
    .FirstOrDefaultAsync(b => b.Id == query.Id, ct)
    ?? throw new NotFoundException("Brand not found");

// 校验数据范围：当前用户是否能看到该数据的创建者所在部门
var filter = await _scopeService.GetFilterAsync(ct);
if (!filter.IsAllDepartments
    && !filter.VisibleUserIds!.Contains(entity.CreatedBy!))
{
    throw new ForbiddenException("Access denied");
}
```

## 六、部门树查询与缓存策略

部门树是高频读取、低频修改的数据，需要缓存以避免每次请求递归查库：

```csharp
// IDepartmentTreeService 内部实现
public async Task<HashSet<Guid>> GetDescendantIdsAsync(
    Guid departmentId, CancellationToken ct)
{
    return await _cache.GetOrCreateAsync(
        $"dept:descendants:{departmentId}",
        async (entry) =>
        {
            entry.Tags = ["departments"];
            // PostgreSQL 递归 CTE
            var sql = """
                WITH RECURSIVE dept_tree AS (
                    SELECT "Id" FROM "organization"."Departments"
                    WHERE "Id" = {0} AND "IsDeleted" = FALSE
                    UNION ALL
                    SELECT d."Id" FROM "organization"."Departments" d
                    INNER JOIN dept_tree dt ON d."ParentId" = dt."Id"
                    WHERE d."IsDeleted" = FALSE
                )
                SELECT "Id" FROM dept_tree
                """;
            // ... EF Core FromSqlRaw 或 Dapper 执行
        },
        ct);
}
```

部门变更（增/删/改）时，通过 `cache.RemoveByTag("departments")` 批量失效。

## 九、风险与缓解

| 风险 | 缓解 |
|------|------|
| `IClaimsTransformation` 每次请求都查库 | HybridCache 缓存用户-部门映射，缓存 key = `user:dept:{userId}`，部门变更时失效 |
| `CreatedBy` 为 null（历史数据/种子数据） | 过滤条件用 `CreatedBy == null OR CreatedBy IN (...)`，null 视为全可见 |
| 大部门 `VisibleUserIds` 集合过大导致 SQL 膨胀 | PostgreSQL `= ANY(array)` 参数化查询，10k 用户亦可承受；超过此规模用临时表 JOIN |
| `VisibleUserIds.Contains(CreatedBy)` 在 EF 中翻译为 `WHERE IN (...)` 而非参数化 | 实测验证 SQL 翻译；必要时使用 `EF.Functions.Contains` 或原始 SQL |
| 部门删除后用户数据漂移 | 部门实行软删除（`ISoftDeletable`），已关联数据不受影响；用户移入新部门后重新生效 |
| `IAuditableEntity.CreatedBy` 是 `string?` 而 `FshUser.Id` 是 `string`（GUID 字符串） | 类型一致（都是 GUID 字符串），无转换成本 |
